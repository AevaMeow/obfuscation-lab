# Лабораторная работа: VM-обфускация crackme

## Идея лабораторной

Основная тема лабораторной работы — обфускация методом виртуализации.
Цель состоит в том, чтобы перенести критическую логику проверки ключа
из обычного машинного кода в байткод собственной виртуальной машины.

Чистая программа `crackme_clean.c` проверяет ключ обычным сравнением.
В `crackme_vm.c` эта проверка представлена программой для кастомной
стековой VM. В итоговый ELF-файл встраиваются интерпретатор VM и
зашифрованный массив байткода. Процессор x86-64 выполняет
интерпретатор, а интерпретатор по очереди исполняет инструкции
виртуальной программы проверки ключа.

Таким образом, при анализе бинарника нельзя сразу увидеть обычную
цепочку сравнений символов. Сначала необходимо найти интерпретатор,
восстановить архитектуру VM, определить значения и назначение opcode,
понять алгоритм расшифровки, извлечь VM-bytecode из секции `.data` и
только после этого анализировать виртуализированную проверку.

Архитектура VM, набор инструкций и значения opcode являются
фиксированными. При этом VM-программа, то есть последовательность
байткода с конкретной логикой проверки, может быть другой. Solver
получает байткод конкретной программы, символически исполняет его и
использует Z3 для поиска подходящего ключа.

Остальные техники — шифрование строк, opaque predicate, ложные ветки,
усложнённые константы и control-flow flattening — используются как
дополнительные средства, затрудняющие поиск и анализ основного
виртуализированного участка.

Правильный ключ имеет формат:

```text
XXXX-XXXX-XXXX-XXXX
```

Его длина равна 19 символам, дефисы находятся на позициях 4, 9 и 14.

Файлы проекта:

```text
vm/crackme_clean.c  — исходная необфусцированная проверка
vm/crackme_vm.c     — проверка через собственную VM
bin/crackme_ida     — обфусцированный ELF для анализа в IDA
solver/solver.c     — символический solver на C с использованием Z3
solver/solver       — собранный solver
```

## Использованные методы обфускации

### Шифрование строк

Сообщения `Correct`, `Wrong` и `Usage` представлены массивами
зашифрованных байтов. Функция `print_encrypted_message` расшифровывает
их только во время вывода.

Поэтому команда `strings` не должна находить эти сообщения в
`crackme_ida`.

### Усложнённые константы

Длина ключа и позиции дефисов не везде записаны непосредственно.
Например, число 19 вычисляется как:

```c
(3 * 7) - 2
```

Нулевая добавка зависит от пользовательского ввода:

```c
volatile int zero = input[0] ^ input[0];
```

### Volatile и зависимость от ввода

Переменные с `volatile` заставляют компилятор сохранять вычисления.
Некоторые выражения формально зависят от введённого ключа или
глобального состояния, хотя их результат заранее известен.

### Opaque predicate

Используется выражение:

```c
(x * x + x) & 1
```

Число `x * x + x` всегда чётное, поэтому результат всегда равен нулю.
Для анализатора условие выглядит зависящим от ввода, но фактически
настоящая проверка всегда направляется в VM.

### Ложные ветки

Функция `fake_key_check` вычисляет правдоподобный хеш ключа. Она
выглядит как возможная проверка, но находится на недостижимом пути,
созданном opaque predicate.

### Уплощение потока управления

Функции `check_key_format_flattened` и `check_key` реализованы как
циклы с `switch` и переменной `state`.

Вместо последовательных `if` декомпилятор показывает автомат
состояний с большим графом переходов. Такой приём называется
control-flow flattening, или уплощением графа управления.

### Виртуализация

Проверка каждого символа ключа записана не обычными сравнениями C, а
инструкциями собственной VM. Функция `execute_vm` читает opcode,
выполняет его и изменяет виртуальный стек.

Аналитику необходимо сначала восстановить устройство интерпретатора,
затем расшифровать байткод и только после этого анализировать проверку
ключа.

### Шифрование VM-bytecode

Массив `encrypted_vm_bytecode` содержит не открытые opcode, а
зашифрованные байты.

Байт в позиции `position` расшифровывается формулой:

```c
decoded = encrypted[position]
          ^ (((position * 17) + 0x5A) ^ 0xA5);
```

Ключевой поток зависит от позиции, поэтому фрагмент solver должен
получать начиная с нулевого байта VM-программы.

### XOR при сравнении ключа

Символ ключа не сравнивается с открытым ASCII-кодом. Для каждой
позиции VM выполняет проверку вида:

```text
(input[i] XOR mask) == encoded_value
```

Где:

```text
encoded_value = correct_character XOR mask
```

### Удаление символов

После сборки для `crackme_ida` выполняется:

```bash
strip --strip-all bin/crackme_ida
```

Названия функций из C-файла удаляются. IDA присваивает им имена
вроде `sub_4012E1`, а локальным переменным — `var_...`.

## Какая VM используется

В проекте используется кастомная стековая байт-ориентированная
виртуальная машина.

### Стековая

Операнды передаются через массив `stack[256]`.

Например, `XOR` снимает два верхних значения:

```text
right = pop()
left  = pop()
push(left XOR right)
```

В регистровой VM инструкции содержали бы номера виртуальных
регистров. В аккумуляторной VM большинство операций работало бы с
одним выделенным аккумулятором. Здесь используются именно стек и
указатель `stack_p`.

### Байт-ориентированная

Каждый opcode занимает один байт. Операнды `LOAD_CHAR`,
`PUSH_CONST`, `JUNK` и `DEAD` также занимают по одному байту.

Инструкции имеют переменную длину:

- один байт: `XOR`, `CMP_EQ`, `AND`, `RET`;
- два байта: opcode и операнд у `LOAD_CHAR`, `PUSH_CONST`, `JUNK`,
  `DEAD`.

VM-bytecode является машинным языком только для нашей виртуальной
машины. Процессор x86-64 напрямую его не понимает. Его исполняет
интерпретатор `execute_vm`, скомпилированный в обычный машинный код.

## Opcode виртуальной машины

| Opcode | Имя | Описание |
|---|---|---|
| `0xA7` | `LOAD_CHAR i` | Кладёт `input[i]` на стек |
| `0x3D` | `PUSH_CONST value` | Кладёт однобайтовую константу на стек |
| `0xE1` | `XOR` | Снимает два значения и кладёт их XOR |
| `0x64` | `CMP_EQ` | Сравнивает два значения и кладёт `0` или `1` |
| `0x9B` | `AND` | Выполняет логическое AND двух результатов |
| `0x2C` | `RET` | Возвращает верхнее значение стека |
| `0xD1` | `JUNK value` | Изменяет фиктивное состояние, не влияя на ключ |
| `0x6D` | `DEAD offset` | Создаёт ложный переход через opaque predicate |

## Как VM проверяет ключ

Для одной позиции ключа логика выглядит так:

```text
LOAD_CHAR i
PUSH_CONST mask
XOR
JUNK value
PUSH_CONST encoded_value
CMP_EQ
```

Для следующего символа формируется такое же сравнение. Результаты всех
19 сравнений объединяются инструкциями `AND`. Последняя инструкция
`RET` возвращает единицу только тогда, когда верны все сравнения.

Пример проверки первого символа:

```text
input[0] XOR 0x6D == 0x26
```

Из этого следует:

```text
input[0] = 0x26 XOR 0x6D = 0x4B = 'K'
```

## Принцип работы программы

1. `main` получает ключ из `argv[1]`.
2. `check_key` запускает flattened-автомат.
3. `check_key_format_flattened` проверяет длину и позиции дефисов.
4. `opaque_predicate` направляет выполнение в настоящий VM-путь.
5. `execute_vm` устанавливает `ip` и `stack_p` в ноль.
6. `vm_fetch_byte` читает и расшифровывает очередной байт.
7. `switch` выбирает обработчик соответствующего opcode.
8. VM формирует на стеке 19 результатов сравнений.
9. `AND` объединяет их, а `RET` возвращает итог.
10. `main` расшифровывает и выводит `Correct` или `Wrong`.

## Принцип работы Z3 solver

Solver не открывает ELF и не ищет секцию `.data`. Пользователь
самостоятельно передаёт найденный в IDA фрагмент как непрерывную
hex-строку.

Solver выполняет следующие действия:

1. Преобразует каждые два hex-символа в один байт.
2. Расшифровывает байткод тем же позиционным ключевым потоком.
3. Создаёт в Z3 19 символьных восьмибитных переменных:
   `key_00` ... `key_18`.
4. Символически исполняет инструкции VM.
5. `LOAD_CHAR` кладёт на символический стек переменную ключа.
6. `PUSH_CONST` кладёт восьмибитную константу.
7. `XOR`, `CMP_EQ` и `AND` создают соответствующие выражения Z3.
8. Выражение с вершины стека при `RET` добавляется как обязательное
   ограничение.
9. Z3 проверяет формулу и при результате `sat` возвращает модель.
10. Значения `key_00` ... `key_18` образуют найденный ключ.

Это не перебор. Z3 решает систему ограничений, восстановленную из
семантики VM-bytecode.

### Зачем solver использует функции Z3

C API библиотеки Z3 является низкоуровневым. Z3 не понимает
VM-bytecode и назначение opcode самостоятельно. Solver должен
перевести каждую инструкцию нашей VM в соответствующее выражение Z3.

Основные функции Z3:

- `Z3_mk_bv_sort` создаёт тип восьмибитного значения;
- `Z3_mk_const` создаёт неизвестные символы ключа;
- `Z3_mk_unsigned_int` создаёт восьмибитную константу;
- `Z3_mk_bvxor` строит символическое выражение XOR;
- `Z3_mk_eq` строит условие равенства;
- `Z3_mk_and` объединяет результаты сравнений;
- `Z3_solver_assert` добавляет итоговое условие в solver;
- `Z3_solver_check` проверяет выполнимость и возвращает `sat` или
  `unsat`;
- `Z3_model_eval` извлекает найденные значения символов ключа из
  модели.

Остальные вызовы создают контекст, объект solver и модель, а также
управляют временем их жизни.

Solver рассчитан на байткод именно этой лабораторной и предполагает,
что пользователь правильно выделил массив в IDA. Поэтому в нём
оставлены только базовые проверки границ массива, индекса ключа и
виртуального стека. Назначение opcode и длина ключа уже известны из
предварительного анализа `crackme_ida`.

## Сборка

Установить компилятор и C API Z3:

```bash
sudo apt install build-essential libz3-dev
```

Собрать проект:

```bash
cd ~/obfuscation-lab
make clean
make
```

## Запуск crackme

Запуск VM-версии:

```bash
./bin/crackme_ida AAAA-BBBB-CCCC-DDDD
./bin/crackme_ida K1R1-0BF5-VM42-C0DE
```

## Запуск solver

В IDA открыть секцию `.data` и найти начало массива VM-bytecode.
В текущей сборке массив состоит из 259 байтов и начинается с `2E`.

Передать все байты как одну непрерывную hex-строку. Для 259 байтов
строка должна содержать 518 hex-символов:

```bash
HEX="2EFE7E28066784A5..."
./solver/solver "$HEX"
```

Пробелы, запятые и префиксы `0x` не допускаются.

Вывести только ключ:

```bash
./solver/solver -q "$HEX"
```

Передать найденный ключ в crackme:

```bash
./bin/crackme_ida "$(./solver/solver -q "$HEX")"
```

## Проверка обфускации

Проверить открытые строки:

```bash
strings bin/crackme_ida | grep -E "K1R1|Correct|Wrong|Usage"
```

Проверить удаление символов:

```bash
nm bin/crackme_ida
```

Ожидаемый результат:

```text
nm: bin/crackme_ida: no symbols
```

Дизассемблирование:

```bash
objdump -d bin/crackme_ida
```

Для интерактивного анализа открыть `bin/crackme_ida` в IDA Free.
