# Лабораторная работа по обфускации

## Идея лабораторной

Идея заключается в обфускации методом виртуализации. 
Критическая логика проверки ключа переносится из обычного машинного кода 
в байткод собственной виртуальной машины.

Чистая программа `crackme_clean.c` проверяет ключ обычным сравнением.
В `crackme_vm.c` эта проверка представлена программой для кастомной
стековой VM. В итоговый ELF-файл встраиваются интерпретатор VM и
зашифрованный массив байткода. Процессор x86-64 выполняет
интерпретатор, а интерпретатор по очереди исполняет инструкции
виртуальной программы проверки ключа.

Правильный ключ имеет формат:

```text
XXXX-XXXX-XXXX-XXXX
```
Длина 19 символов, дефисы находятся на позициях 4, 9 и 14.

## Использованные методы обфускации

### Шифрование строк

Сообщения `Correct`, `Wrong` и `Usage` представлены массивами
зашифрованных байтов. Функция `print_encrypted_message` расшифровывает
их только во время вывода.

### Усложнённые константы

Длина ключа и позиции дефисов не везде записаны явно.
Например, число 19 вычисляется так:

```c
(3 * 7) - 2
```

Так же присутствует константа, зависящая от пользовательского ввода:

```c
volatile int zero = input[0] ^ input[0];
```

### Volatile и зависимость от ввода

Переменные с `volatile` заставляют компилятор сохранять вычисления.
Некоторые выражения формально зависят от введённого ключа или
глобального состояния, хотя их результат заранее известен.

### Opaque predicate

Используется выражение:

```c
(x * x + x) & 1
```

Число `x * x + x` всегда чётное, поэтому результат всегда равен нулю.
Для анализатора условие выглядит зависящим от ввода, но фактически
настоящая проверка всегда направляется в VM.

### Ложные ветки

Функция `fake_key_check` вычисляет правдоподобный хеш ключа. Она
выглядит как возможная проверка, но находится на недостижимом пути,
созданном opaque predicate.

### Control-flow flattening

Функции `check_key_format_flattened` и `check_key` реализованы как
циклы с `switch` и переменной `state`.
Вместо последовательных `if` декомпилятор показывает автомат
состояний с большим графом переходов.

### Виртуализация

Проверка каждого символа ключа записана инструкциями собственной VM. 
Функция `execute_vm` читает opcode, выполняет его и изменяет виртуальный стек.

### Шифрование VM-bytecode

Массив `encrypted_vm_bytecode` содержит зашифрованные байты.

Байт в позиции `position` расшифровывается формулой:

```c
decoded = encrypted[position]
          ^ (((position * 17) + 0x5A) ^ 0xA5);
```

### XOR при сравнении ключа

Символ ключа не сравнивается с открытым ASCII-кодом. Для каждой
позиции VM выполняет следующую проверку:

```text
(input[i] XOR mask) == encoded_value
```

Где:

```text
encoded_value = correct_character XOR mask
```

### Удаление символов

После сборки для `crackme_ida` выполняется:

```bash
strip --strip-all bin/crackme_ida
```

Названия функций из C-файла удаляются. IDA присваивает им имена
вроде `sub_4012E1`, а локальным переменным — `var_...`.

## Используемая VM

В проекте используется кастомная стековая однобайтовая VM.

Операнды передаются через массив `stack[256]`.
`XOR` снимает два верхних значения:

```text
right = pop()
left  = pop()
push(left XOR right)
```
Каждый opcode занимает один байт. Операнды `LOAD_CHAR`,
`PUSH_CONST`, `JUNK` и `DEAD` также занимают по одному байту.

Инструкции имеют переменную длину:

- один байт: `XOR`, `CMP_EQ`, `AND`, `RET`;
- два байта: opcode и операнд у `LOAD_CHAR`, `PUSH_CONST`, `JUNK`,
  `DEAD`.

## Список opcode

| Opcode | Имя | Описание |
|---|---|---|
| `0xA7` | `LOAD_CHAR i` | Кладёт `input[i]` на стек |
| `0x3D` | `PUSH_CONST value` | Кладёт однобайтовую константу на стек |
| `0xE1` | `XOR` | Снимает два значения и кладёт их XOR |
| `0x64` | `CMP_EQ` | Сравнивает два значения и кладёт `0` или `1` |
| `0x9B` | `AND` | Выполняет логическое AND двух результатов |
| `0x2C` | `RET` | Возвращает верхнее значение стека |
| `0xD1` | `JUNK value` | Изменяет фиктивное состояние, не влияя на ключ |
| `0x6D` | `DEAD offset` | Создаёт ложный переход через opaque predicate |

## Проверка ключа 

Для одной позиции ключа логика выглядит так:

```text
LOAD_CHAR i
PUSH_CONST mask
XOR
JUNK value
PUSH_CONST encoded_value
CMP_EQ
```

Для следующего символа формируется такое же сравнение. Результаты всех
19 сравнений объединяются инструкциями `AND`. Последняя инструкция
`RET` возвращает единицу только тогда, когда верны все сравнения.

Пример проверки первого символа:

```text
input[0] XOR 0x6D == 0x26
```
Следовательно:

```text
input[0] = 0x26 XOR 0x6D = 0x4B = 'K'
```

## Принцип работы программы

1. `main` получает ключ из `argv[1]`.
2. `check_key` запускает flattened-автомат.
3. `check_key_format_flattened` проверяет длину и позиции дефисов.
4. `opaque_predicate` направляет выполнение в настоящий VM-путь.
5. `execute_vm` устанавливает `ip` и `stack_p` в ноль.
6. `vm_fetch_byte` читает и расшифровывает очередной байт.
7. `switch` выбирает обработчик соответствующего opcode.
8. VM формирует на стеке 19 результатов сравнений.
9. `AND` объединяет их, а `RET` возвращает итог.
10. `main` расшифровывает и выводит `Correct` или `Wrong`.

## Принцип работы Z3 solver

Изначально пользователь вручную реверсит бинарь и восстанавливает 
логику работы программы, длину ключа, значения и назначение opcode,
и т.д. 
Далее на вход солверу подается байткод конкретной программы проверки в формате
hex (unspaced), после чего z3 решает систему ограничений, восстановленную
из семантики бинаря.

Solver выполняет следующие действия:

1. Преобразует каждые два hex-символа в один байт.
2. Расшифровывает байткод тем же позиционным ключевым потоком.
3. Создаёт в Z3 19 символьных восьмибитных переменных:
   `key_00` ... `key_18`.
4. Символически исполняет инструкции VM.
5. `LOAD_CHAR` кладёт на символический стек переменную ключа.
6. `PUSH_CONST` кладёт восьмибитную константу.
7. `XOR`, `CMP_EQ` и `AND` создают соответствующие выражения Z3.
8. Выражение с вершины стека при `RET` добавляется как обязательное
   ограничение.
9. Z3 проверяет формулу и при результате `sat` возвращает модель.
10. Значения `key_00` ... `key_18` образуют найденный ключ.

### API Z3 (Python)

Solver реализован на Python с библиотекой `z3-solver`. Используются
следующие средства Z3:

- `BitVec("key_NN", 8)` создаёт неизвестный восьмибитный символ ключа;
- `BitVecVal(value, 8)` создаёт восьмибитную константу;
- оператор `^` над `BitVec` строит символический XOR;
- оператор `==` строит условие равенства (`CMP_EQ`);
- `And(...)` объединяет результаты сравнений (`AND`);
- `Solver()` создаёт объект солвера;
- `solver.add(expr)` добавляет итоговое условие (выражение с вершины
  стека при `RET`);
- `solver.check()` проверяет выполнимость и возвращает `sat` или
  `unsat`;
- `solver.model()` и `model[var].as_long()` извлекают найденные
  значения символов ключа.

Hex-строка разбирается встроенным `bytes.fromhex`.

Solver рассчитан на байткод именно этой лабораторной и предполагает,
что пользователь правильно выделил массив в IDA.

## Сборка

Зависимости. Для Python-солвера достаточно `z3-solver`; пакеты
`build-essential` и `libz3-dev` нужны только для сборки исторической
C-версии солвера через `make`:

```bash
pip install z3-solver
sudo apt install build-essential libz3-dev   # только для solver/solver.c
```

Сборка проекта (crackme, генератор и C-солвер):

```bash
cd ~/obfuscation-lab
make clean
make
```

Python-солвер собирать не нужно — он запускается напрямую.

## Запуск crackme

Запуск VM-версии:

```bash
./bin/crackme_ida AAAA-BBBB-CCCC-DDDD
./bin/crackme_ida K1R1-0BF5-VM42-C0DE
```

## Запуск solver

В IDA открыть секцию `.data` и найти начало массива VM-bytecode.
В текущей сборке массив состоит из 259 байтов и начинается с `2E`.

Передать все байты как одну hex строку без пробелов. Для 259 байтов
строка должна содержать 518 hex символов.

Solver реализован на Python (`solver/solver.py`, библиотека `z3-solver`):

```bash
HEX="2EFE7E28066784A5..."
python3 solver/solver.py "$HEX"
```

Историческая версия на C (`solver/solver.c`, линкуется с `libz3`)
сохранена и собирается через `make`. Обе версии принимают одинаковый
hex-вход и выдают одинаковый ключ.

## Генератор байткода

`generator/bytecode_generator.c` собирает `encrypted_vm_bytecode` для
произвольного ключа. На вход подаётся **строка ключа**, на выходе —
готовый C-массив `encrypted_vm_bytecode` для вставки в `crackme_vm.c`.

```bash
./generator/bytecode_generator K1R1-0BF5-VM42-C0DE
```

Генератор:

1. Для каждого символа `i` вычисляет маску `mask = (0x6D + 29*i) & 0xFF`
   и `encoded = key[i] XOR mask`.
2. Эмитит для позиции инструкции
   `JUNK / [DEAD] / LOAD_CHAR i / PUSH_CONST mask / XOR /
   JUNK / PUSH_CONST encoded / CMP_EQ / [AND]`.
3. Завершает программу инструкцией `RET`.
4. Шифрует весь массив позиционным ключевым потоком
   `(((position * 17) + 0x5A) ^ 0xA5)`.
5. Печатает результат в консоль.

Для ключа `K1R1-0BF5-VM42-C0DE` генератор воспроизводит ровно тот
байткод (259 байтов), который зашит в `crackme_vm.c`.
